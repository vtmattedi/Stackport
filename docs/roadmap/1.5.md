## P1 — Update regression report, restore points and Restore

This carries forward the 1.3.0 networking-incident follow-up, including the original acceptance model in [the postmortem](../incidents/1.3.0-network-outage.md#p1-in-detail-planned-for-15). It protects **updates to the Stackport application and host-managed routing state**, not migration/backup of an entire installation.

### Regression report

- `stackport update` probes each relevant route **before the swap and after it**. The baseline runs from the staged new image against the live Docker/Nginx environment, between the pre-update database snapshot and the swap, and uses the backed-up old route list.
- Compare like for like: a route that was already down is reported separately rather than blamed on the update. A healthy-to-broken route is a newly introduced regression. Include diagnostic causes such as missing DNS alias, refused connection and timeout.
- Surface the result in CLI output and the UI/System update summary.
- **Do not automatically undo an update solely because a project route regressed.** Preserve the existing automatic rollback rule for a newly installed Stackport version that cannot start or report healthy/ready. No automatic incident notification is required by this workstream.

### Infrastructure restore point

Before the update, record what a release may change **outside its image**:

- Docker networks, attachments and service aliases;
- TCP forwarding/proxy containers and associated state;
- Nginx generated configuration and relevant templates;
- any rewritten/augmented Compose files and routing state;
- the existing pre-update database backup and the old application/image revision.

Version these snapshots and ensure that the source and intended target installation are unambiguous. Avoid treating an update snapshot as a portable full workload backup.

### Operator-controlled Restore

- Provide a preview and operator confirmation via **System UI and host CLI** (usable if the web app cannot start).
- Restore the previous application revision and replay affected network/routing/proxy configuration from the recorded infrastructure state. Validate the result and report failures.
- **Database restoration is an independent, off-by-default option**. Clearly explain that choosing it discards database changes made since the update (deployments, audit, settings, etc.). Reuse safe backup primitives delivered in 1.4 where appropriate.
- Plan retention/pruning from real observed sizes; the historical plan proposed keeping the last two restore points. Never delete an in-use or just-created recovery point.
- Validate route behavior, failure modes and recovery with real Docker hosts and multiple projects, not merely mocked Nginx configuration.

## A2 — Scheduled off-host backups (deferred candidate)

**Not committed to 1.5.** This is held here so the prior 1.4 backlog is not lost.

The manual portable backup/restore levels are covered by 1.4. Scheduling, external storage providers and backup retention have distinct multi-instance design challenges. Before implementation, decide:

- Whether automation is per instance, how each independent peer owns its schedules and encrypted backup keys, and how to avoid duplicate jobs or recursive backups of connected peers.
- Which of the three backup levels can run safely unattended, especially application data requiring writer quiescence/database-native backups.
- Remote destination and encryption/key recovery, retention, deduplication, size/bandwidth, integrity checks, restore drills and notification requirements.
- Permissions and isolation so a managing peer cannot silently exfiltrate another instance's full configuration or all workload data.

Do not put these capabilities into 1.4 as a prerequisite for migrating from VPS-1 to VPS-2. A manual verified export to an independently controlled destination is sufficient there.

## Other backlog (not automatically part of 1.5)

Passkeys, MCP Phase 2/granular tool authorization, Docker socket containment (S11), egress restrictions (S10), multi-branch project deployment, repository configuration files and feature/UI cleanups remain in their own existing backlogs. Their sequencing and release inclusion need separate decisions.
